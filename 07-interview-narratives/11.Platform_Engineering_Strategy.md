# Platform Engineering & DevEx Strategy

Platform Engineering is the transition from "Operations" (putting out fires) to "Engineering" (building products for other engineers). At a Staff level, your customer is the internal development team.

## 1. How do you convince feature teams to adopt your platform / tooling?
**Narrative**: You cannot force adoption through mandates; you must win adoption through superior Developer Experience (DevEx). Mandates create resentment; golden paths create velocity.

**Action**:
- I build **Paved Roads** (or Golden Paths). If a team uses my CI/CD pipeline and my logging library, they get alerting, tracing, automatic scaling, and compliance checks *for free*.
- If they want to build their own bespoke solution, they are allowed to—but they take on the operational burden (pagers, security patching). 
- I treat the internal platform like a SaaS product: I do user research (with developers), write documentation, and track onboarding metrics.

## 2. What is your philosophy on CI/CD for hundreds of microservices?
**Narrative**: CI/CD should be invisible, boring, and highly standardized.

**Action**:
- **Decouple CI and CD**: 
  - CI (Continuous Integration - e.g., GitHub Actions) tests code and builds immutable Docker images.
  - CD (Continuous Deployment - e.g., ArgoCD) uses GitOps. The deployment state is defined declaratively in a separate git repo. ArgoCD constantly reconciles the cluster state with the Git repo.
- **Standardized Templates**: Instead of 100 teams writing 100 different Jenkinsfiles, the platform team provides a central Helm chart or template. Teams only provide a `values.yaml` file to inject their specific environment variables.
- **Progressive Delivery**: Nobody should be deploying straight to production. We use tools like Flagger to automate Canary deployments. Traffic is shifted to the new version (10%, 50%, 100%) and automatically rolled back if error rates spike.

## 3. How do you manage infrastructure drift?
**Narrative**: "ClickOps" (clicking around the AWS console) is banned for production databases or infrastructure. 

**Action**:
- **Infrastructure as Code (IaC)**: Everything must be in Terraform or Crossplane.
- **Drift Detection**: We run automated jobs (e.g., spaced Terraform plans) every day to alert us if the cloud environment deviates from Git.
- **Ephemeral Environments**: The true test of no-drift is the ability to spin up an entire replica of production (minus PII data) in an isolated VPC in under 30 minutes using the IaC.

## 4. How do you shift security left?
**Narrative**: Security cannot be a gatekeeper at the end of the deployment cycle; that slows down delivery.

**Action**:
- Integrate SAST (Static Analysis) and dependency vulnerability scanning (Dependabot/Snyk) directly into the PR checks.
- If a high-severity CVE is detected, the PR fails automatically. This gives developers immediate feedback within their IDE/Git workflow, rather than waiting for a security review a week later.
