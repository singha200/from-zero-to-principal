# Performance & Optimization Narratives

Staff and Principal engineers frequently dive deep into systems that are misbehaving at scale—systems that work fine for 100 users but collapse at 100,000. 

## 1. Tell me about a time you hunted down a complex performance issue.
**Context**: One of our Java microservices was experiencing massive latency spikes (P99 latency jumped from 50ms to 2000ms) every few minutes, but CPU and Memory *averages* looked completely fine.

**Action (Investigation)**:
- I knew looking at 1-minute averages hides micro-bursts. I drilled down into 1-second resolution metrics.
- I noticed the JVM was undergoing massive "Stop The World" Garbage Collection (GC) pauses exactly when the latency spiked.
- Used a profiler (e.g., JFR or async-profiler) and generated a Flame Graph to see what was allocating so much memory so quickly.
- Discovered an ORM (Hibernate) issue: a single database call was fetching thousands of related rows into memory (N+1 query problem) on every user login, only to discard 99% of them in code.

**Action (Resolution)**:
- Rewrote the specific query to use targeted `JOIN`s and only fetch necessary columns. 
- P99 latency dropped instantly to 40ms, and CPU utilization halved.

## 2. How do you approach cloud cost optimization?
**Narrative**: Cost is a first-class engineering metric, equal to latency and throughput. 

**Action**:
- **Visibility**: First, I implement strict tagging policies across all infrastructure (via Terraform/Pulumi) so we know *who* is spending *what*. I build a dashboard mapping cloud cost to business metrics (e.g., "Cost per 1,000 transactions") rather than just showing raw AWS bills.
- **Quick Wins**: Implement lifecycle policies on S3 (move old logs to Glacier), identify unttached EBS volumes, and switch non-prod environments to Spot Instances.
- **Architectural Wins**: Move an over-provisioned cluster of EC2 instances to Graviton (ARM) processors for an immediate 20% price-performance gain. Optimize horizontal scaling so we scale down aggressively at night when traffic is low.

## 3. How do you handle a database that has grown too large for a single master?
**Narrative**: Sharding is the absolute last resort due to its immense complexity.

**Action**:
- **Step 1:** Add Read Replicas and route all analytical / read-only traffic there.
- **Step 2:** Optimize queries, add indexes, and implement aggressive caching (Redis/Memcached) for hot data.
- **Step 3:** Archive old/dead data to cold storage (e.g., moving orders older than 2 years to S3/Athena).
- **Step 4:** Vertical Scaling (get a bigger instance type).
- **Step 5 (Final Resort):** If all else fails, implement application-level Sharding (e.g., partitioning users by Region or Hashing their UUID) or migrate to a native distributed database like CockroachDB or Cassandra.

## 4. What is the most important metric when tuning an application?
**Narrative**: Averages lie. I look at percentiles.

**Explanation**: 
If the *average* latency is 100ms, but the *P99* (99th percentile) latency is 5 seconds, it means 1 in 100 users is having a terrible experience. At scale (say, 10 million requests), that’s 100,000 terrible experiences. I optimize for the P99 or P99.9, not the average.
