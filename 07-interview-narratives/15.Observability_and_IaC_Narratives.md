# Observability & Infrastructure Narratives

## 1. Tell me about a time you fixed a critical issue with your monitoring stack.
**Context**: We had 15 Kubernetes clusters feeding data into independent Prometheus instances. As traffic grew 5x over the holidays, our main production Prometheus pod kept crashing under OOM (Out Of Memory) pressure, leaving us totally blind during peak business hours.

**Action (Triage & Resolution)**:
- Investigated the TSDB and discovered "High Cardinality Explosions." Developers had added an `order_id` label to a Prometheus counter. This created millions of unique, one-off time series that Prometheus had to hold in memory.
- Implemented **Prometheus Relabeling Drop Rules** to immediately drop any metric coming from that service containing the `order_id` label, instantly stabilizing the pod.

**Systemic Fix (Staff Action)**:
- We couldn't keep fighting cardinality fires, and looking across 15 Grafana instances was unsustainable.
- I championed and led the migration to **Thanos**. We deployed Thanos Sidecars to all 15 clusters and stood up a central Thanos-Query component. 
- We pushed historical data aggressively to S3 via the Thanos Store component, shrinking Prometheus local retention from 30 days to 24 hours. The OOM issues vanished, cloud block storage costs dropped by 80%, and engineers finally had a single pane of glass to query metrics globally.

## 2. Tell me about navigating Infrastructure-as-Code drift.
**Context**: Before our major deployment event, a junior engineer had manually updated an AWS Security Group in the console to troubleshoot a connection. Six weeks later, when our CI/CD pipeline ran a routine Terraform update for a completely unrelated tag change, Terraform reverted the Security Group back to the state file's truth. The database connection dropped, causing a SEV-1 outage.

**Action**:
- Restored the Security Group immediately to stop the bleeding. 
- **The Culture Fix**: I prohibited manual AWS Console modifications. To enforce this, we tied IAM roles strictly to the Terraform CI/CD pipeline and revoked write access to AWS for human users.
- **The Tech Fix**: Moving to "Read-Only" AWS console access isn't enough; we needed constant reconciliation. We began an initiative to migrate core, volatile infrastructure (like IAM, SGs, SQS queues) out of Terraform and into **Crossplane**. By managing those resources as Kubernetes manifests, Crossplane actively enforced the state out of Git every 30 seconds. If anyone somehow bypassed IAM and modified the console, Crossplane reverted it instantly, ensuring zero configuration drift.

## 3. How do you scale Terraform for 100+ developers?
**Narrative**: "Monolithic state files are a ticking time bomb."

**Action**:
- When I joined, the company had one giant `production.tfstate` file managing everything from Route53 to ECS clusters. Taking 20 minutes just to run a `plan` was unacceptable.
- I broke the monolith into micro-states based on volatility.
  - **Tier 1 (Core Infra)**: VPCs, Subnets (Changes rarely).
  - **Tier 2 (Shared Data)**: RDS, ElastiCache (Changes occasionally).
  - **Tier 3 (Application Layer)**: ECS Task Definitions, ALB Rules (Changes daily).
- Used `terraform_remote_state` data sources to loosely couple them. Now, when a developer pushes an app config, the CI pipeline only evaluates Tier 3, running the plan in 30 seconds with absolutely zero risk of destroying the Tier 1 VPC. We further used **Checkov** to enforce static security policies (e.g., Blocking public S3 buckets) directly in the Pull Request before the apply was even allowed.
