# Upgrades & Complex Migrations Narratives

Interviewers love asking about upgrades because they reveal whether you actually operate systems or just build them in theory. Upgrades at scale are painful, and knowing how to navigate that pain is a Staff-level requirement.

## 1. Tell me about a terrible cluster upgrade and how you fixed it.
**Context**: We were doing an in-place upgrade of a production Kubernetes cluster (v1.21 to v1.22—a notorious upgrade because K8s removed several Beta APIs, notably `v1beta1` Ingress).

**The Breakdown**: 
- We successfully upgraded the control plane via EKS. However, immediately after, our ArgoCD sync processes began failing cluster-wide. 
- Over 40 microservices were stuck in an "Out of Sync" state. Their Helm charts were hardcoded to use `networking.k8s.io/v1beta1` for Ingress. Because the API server had removed this endpoint, the cluster rejected the deployments.
- Worse, the CI/CD pipelines to fix these charts were stalled because we had a deployment freeze during the upgrade window.

**Action (Incident Command & Fix)**:
- Halted the Data Plane (Node) upgrades immediately.
- Wrote a quick Bash/`yq` script to automatically parse all 40 repositories, rewrite the Ingress manifests to `networking.k8s.io/v1`, and dynamically open Pull Requests across GitHub.
- Pushed an emergency blanket approval for the PRs to unblock ArgoCD.

**Post-Mortem & Systemic Fix**:
- "Hope is not a strategy." We altered our pre-upgrade workflow.
- Implemented **kubent (Kube-no-trouble)** into an overnight GitHub Actions cron job. If `kubent` detects that *any* branch in our GitOps repo is using an API destined for deprecation in the next K8s release, it sends a Slack alert to the owning team 3 months in advance. We now treat API deprecations like Security Vulnerabilities.

## 2. How do you handle State during aggressive OpenShift Node reboots?
**Narrative**: OpenShift upgrades reboot the underlying CoreOS. You can't avoid it. But stateful applications hate reboots.

**Action**: 
- We had a Kafka cluster running on OpenShift. When the Machine Config Operator (MCO) began draining nodes, it randomly drained two nodes holding Kafka brokers in the same partition replica set simultaneously, causing brief data unavailability.
- **The Fix**: 
  - Mandated the use of strict `PodDisruptionBudgets` (`maxUnavailable: 1`) on the Kafka StatefulSet. Kubelet will now *refuse* the MCO's request to drain the second node until the first broker pod is fully healthy and has rejoined the Kafka quorum.
  - To speed up the uncordoning process, we tuned the `terminationGracePeriodSeconds`. Many Java apps default to 30s, but we wrote explicit PreStop hooks that commanded the Kafka broker to gracefully resign leadership immediately, dropping shutdown time to 5 seconds.

## 3. When do you choose Blue/Green Cluster Migration over an In-Place Upgrade?
**Narrative**: In-place is cheaper and easier, but some blast radiuses are too large. I define a risk threshold.

**Action**:
- I advocate for Blue/Green cluster migrations when:
  1. We are fundamentally changing cluster infrastructure (e.g., migrating the Container Network Interface from Calico to Cilium). 
  2. We have skipped multiple major versions and are too far behind standard upgrade paths.
- **The Execution**:
  - We stand up the new cluster (Green).
  - Since we use full GitOps (ArgoCD/Flux), applying workloads to the Green cluster takes 10 minutes.
  - The real challenge is Data Gravity. For databases, we set up asynchronous, cross-cluster replication (using tools like Crunchy Postgres's pgBackRest or native Kafka MirrorMaker) ahead of time.
  - Cutover involves locking the Blue database to Read-Only, verifying replication is caught up, pointing Route 53 to the Green Ingress, and unlocking the Green database.

## 4. How do you coordinate upgrades with hundreds of disconnected engineering teams?
**Narrative**: The technology is easy; communicating with 100 people is hard.

**Action**:
- **Blackout Windows**: We respect business cycles. No upgrades during Black Friday or End-of-Quarter financial closes.
- **Status Dashboarding**: Instead of mass emails that nobody reads, we built an Internal Developer Portal (like Spotify Backstage). When a developer logs in, they see a giant banner: "Cluster prod-eu-west upgrade on Saturday. Your service `auth-api` is flagged as COMPLIANT. No action needed." 
- We tie upgrade blockers to their deployment capabilities. If a team refuses to fix a deprecated API two weeks before the deadline, we automatically lock their CI/CD pipeline. That creates instant urgency.
