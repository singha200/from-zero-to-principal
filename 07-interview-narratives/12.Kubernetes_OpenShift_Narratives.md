# Kubernetes & OpenShift Narratives

## 1. Diagnosing a Complex Cluster Outage
**Context**: A deployment of a new custom controller caused our entire OpenShift cluster control plane to grind to a halt. Developers couldn't deploy, and the API server was completely unresponsive.

**Action (Triaging)**:
- I bypassed the API server entirely (since `kubectl` was timing out) and SSH’d directly into the Master nodes.
- Checked `journalctl -u kubelet` and the API server logs. I saw extreme latency connecting to Etcd, specifically around leadership elections.
- Checked Etcd metrics and noticed disk sync times were jumping to 500ms (Etcd expects <10ms).
- Why? A misconfigured Custom Resource Definition (CRD) controller from a newly deployed application was in an infinite loop, constantly doing massive `LIST` requests against the entire cluster state instead of caching local objects, flooding the API server, which then hammered Etcd.

**Resolution / Post-Mortem**:
- **Mitigation**: Deleted the offending deployment from the namespace forcibly via API server emergency access.
- **Prevention**: Implemented API Priority and Fairness (APF) to throttle requests from specific service accounts, ensuring the cluster's core components always have API bandwidth over user-created operators.

## 2. Managing OpenShift Upgrades with Zero Downtime
**Narrative**: OpenShift updates the underlying OS (CoreOS) along with K8s components. This means nodes *will* reboot. 

**Action**:
- I designed our workload onboarding policy around node reboots. Teams must prove they can survive a random node termination before they get production access.
- **Mechanism**:
  1. Mandate **Pod Disruption Budgets (PDBs)** to prevent the node drain process from evicting too many pods at once.
  2. Implement **Graceful Shutdowns**: Pods must catch the `SIGTERM` signal, stop accepting new connections, finish processing in-flight requests, and exit cleanly within terminationGracePeriodSeconds (e.g., 30s).
  3. Set up **Pre-Stop Hooks** if the application cannot catch signals properly (e.g., legacy NGINX workers).

## 3. Scaling the Data Plane vs. Control Plane
**Narrative**: Auto-scaling isn't just about spinning up more pods (HPA). If you spin up 50 pods on a full cluster, they just sit in a `Pending` state.

**Action**:
- I implemented the **Cluster Autoscaler** combined with **Karpenter** (or OpenShift MachineAutoscaler) to automatically provision new EC2 instances when pods are stuck in `Pending`.
- **The Staff Twist**: Scaling a node takes 2-4 minutes. If traffic spikes instantly, you are too slow. I implemented **"Pause Pods"** (Overprovisioning): creating low-priority sleep pods that intentionally take up Node space. When a high-priority production pod needs to scale, K8s preempts (kills) the low-priority Pause Pod instantly, avoiding the 4-minute wait for AWS to bring up a new VM.

## 4. OPA (Open Policy Agent) & Kyverno
**Narrative**: You can't rely on humans to review every single YAML file for security.

**Action**:
- Instead of manually checking if a deployment uses the `latest` tag, or runs as `root`, I deployed a Mutating Admission Webhook (Kyverno).
- If a developer tries to apply a naked Pod without a resource limit, the webhook intercepts the API call and injects a default CPU/Mem limit. 
- If they try to deploy an image from an untrusted public registry (e.g., raw docker.io instead of our internal Nexus proxy), the Validating Webhook explicitly blocks the deployment and returns a friendly error message to the developer's terminal.
