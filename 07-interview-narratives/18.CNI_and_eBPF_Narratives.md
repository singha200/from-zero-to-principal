# CNI & eBPF Narratives

When interviewing for Staff/Principal roles, demonstrating knowledge of Linux Kernel mechanics (iptables vs eBPF) separates developers who "use" Kubernetes from Platform Engineers who "build" Kubernetes.

## 1. Tell me about a time you hit the limits of Kubernetes networking.
**Context**: We ran a massive multi-tenant cluster holding over 10,000 K8s Services. Engineers began complaining about bizarre network timeouts. Packets would randomly drop, and basic HTTP requests between pods inside the same cluster were taking 500ms to resolve. 

**Action (Triage & Diagnosis)**:
- I bypassed the application logs and looked at the node-level Linux metrics. CPU usage on the core networking threads was spiked. 
- The cluster was still using the default `kube-proxy` in iptables mode. I dumped the iptables rules (`iptables-save`) and found over 80,000 sequential rules. 
- **The Epiphany**: Every single time a new pod was created or destroyed by the autoscaler, `kube-proxy` had to rewrite the entire 80,000-rule iptables list. During this rewrite (which took a full 2-3 seconds), the kernel would lock, and network packets were delayed or dropped. Iptables evaluates sequentially `O(N)`. We had mathematically hit the limit of 1998 Linux firewall technology.

**Resolution**:
- We initiated a cluster migration to replace the default CNI and `kube-proxy` entirely with **Cilium**. 
- By moving to an **eBPF-based** data plane, routing decisions shifted from sequential iptables evaluation to bounded O(1) hash map lookups directly in the kernel space. 
- Latency dropped from 500ms to <1ms, and the CPU overhead on our worker nodes decreased by 30%, saving us thousands of dollars a month on EC2 costs.

## 2. How do you implement Zero-Trust Egress Security?
**Narrative**: Native Kubernetes only protects *inner-cluster* (east/west) traffic. It fails miserably at protecting *outbound* (north/south) traffic. 

**Context**: Our Security team discovered a vulnerable Node.js pod had been compromised and was aggressively downloading crypto-mining malware from external servers. 

**Action**:
- Security demanded we block all outbound internet traffic unless explicitly allowed. The problem? Standard Kubernetes NetworkPolicies only block based on IP addresses. Modern SaaS APIs (like AWS S3 or Stripe) use DNS names with dynamic IP ranges that change hourly. You cannot write an IP-based firewall rule for s3.amazonaws.com.
- **The Fix**: I leveraged our **Cilium CNI** advanced policies. Because Cilium uses eBPF to inspect traffic in the kernel, it understands DNS.
- I wrote a `CiliumNetworkPolicy` that blocked all egress by default, but allowed outbound connections that matched the FQDN (Fully Qualified Domain Name) `*.stripe.com`. 
- If a pod tried to resolve or hit `malware.com`, the kernel dropped the packet instantly. We achieved strict Zero-Trust egress without forcing HTTP Proxies (like Squid) on the developers.
